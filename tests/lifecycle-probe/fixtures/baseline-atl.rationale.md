# Why `baseline-atl.trace` looks the way it does

Companion to `baseline-atl.trace` (generated by
`python3 tests/lifecycle-probe/make_fixtures.py`; it is reproduced bit-exactly
by that command from `manifest.json` + the `atl_transform` in
`make_fixtures.py`). Pinned Android source of truth:
`refs/tags/android-17.0.0_r1` = `94b4c163b7dfe5ce3607f7bb8456f9573f7de57d`.

PINNED mode (`compare_baseline`) pins exactly one dimension: the per-scenario
Activity-only `.pre`/`.post` framing sequence (`activity_order`). Everything
else in the candidate is still validated per event against the
Android-derived manifest. The baseline therefore has to record the launcher
ordering that ATL really produces for an A -> B -> A launch.

## The ordering ATL really produces

`ATLActivityController` (lane C) is the single owner of lifecycle dispatch; the
native seam only forwards host events. For an A -> B -> A launch the code paths
are:

- `startActivity(B)`: pause A (only when A is resumed) -> B `onCreate`,
  `onStart`, `onRestoreInstanceState` (only when saved state exists),
  `onPostCreate`, `onResume` -> then stop A
  (`moveToState(prev, ON_STOP, false)`), i.e. A is stopped only once B is
  resumed and focused.
- `performFinish(B)`: pause B -> hand the window back, which resumes A
  (`moveToState(A, ON_RESUME)` => `ON_RESTART` then `ON_START` then
  `ON_RESUME`) -> stop B -> destroy B.

Per scenario that is:

```
ActA onPause, ActB onCreate, ActB onStart, ActB onResume,
ActA onStop,
ActB onPause, ActA onRestart, ActA onStart, ActA onResume,
ActB onStop, ActB onDestroy
```

## AOSP alignment

- `ActivityThread.handleLaunchActivity` + `handleStartActivity`
  (`ActivityThread.java:4585-4640`): the launch sequence is pause -> create ->
  restore (only when state exists) -> postCreate -> resume, and the covered
  activity is stopped once the incoming one is resumed: this is AOSP order, not
  an ATL quirk.
- `ActivityThread.callActivityOnStop` (`6310-6394`): a finishing activity is
  never saved, which is why no `onSaveInstanceState` group appears around the
  `ActB onStop` groups.
- `TransactionExecutorHelper.getLifecyclePath` (`68-129`): `ON_STOP` ->
  `ON_RESUME` resolves through `ON_RESTART, ON_START, ON_RESUME`, which is why
  the returning `ActA` carries an `onRestart` group. `ActivityLifecycleCallbacks`
  has no restart callback, so that group is framing-only (no callback tuples).

The extra groups are accepted by the analyzer as ATL-only extras:
`compare_groups` -> `_validate_extra_group` checks their framing phases, their
callback event name (`callback_map[base]`) and Bundle null-ness, while the
observer set stays dynamic. That is why no manifest event list had to change.

The Android-derived manifest groups themselves are untouched: the reference
keeps the recorded Android ordering for these scenarios, and the candidate is
reported with an explicit `DIVERGENCE` line for the scenarios whose Activity
ordering differs from that reference.

## Scenario-derived observers

The extra groups take their observer list from the scenario's own
`ActA#1 onResume` group, i.e. the registration set in force **after** any
mid-dispatch register/unregister. That keeps the LC semantics of each scenario:

| Scenario | observers in the extra groups | why |
| --- | --- | --- |
| S2, S4.1, S3D1, L-EQUALS | `AppObs-A`, `AppObs-B` | both registered for the whole scenario |
| S4.2, S4.5 | `AppObs-A` only | `AppObs-B` was unregistered before the launch |
| S4.3 | `AppObs-A`, `AppObs-C`, `AppObs-C` | duplicate registration is additive |
| S4.4 | `AppObs-A`, `AppObs-C` | `AppObs-C` registered, `AppObs-B` removed |
| L-SNAP | `AppObs-A`, `AppObs-MUT` | `AppObs-VICT` was removed during the `ActB#8` create dispatch |
| L-REGD | `AppObs-A`, `AppObs-REG`, `AppObs-NEW` | `AppObs-NEW` joins from `onStart` onwards |

Scenarios with no covered pause (`INIT`/S1 preamble) and the FT-only scenarios
are returned unchanged, as is the terminal `L-THROW` prefix (the `ActB#11`
create throws, so the launch never reaches the extra groups).
